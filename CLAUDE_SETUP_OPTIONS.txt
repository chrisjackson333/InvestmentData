3. SUBAGENTS
=====================================================================
What they are: specialized personas with their own tool access and
system prompt, defined in .claude/agents/*.md. I dispatch work to them
via the Agent tool when a task matches their description. Unlike a
skill (a technique I apply myself), a subagent runs semi-independently
and reports back.

Relevant candidate for this repo: a "domain-boundary-reviewer" subagent
— given DomainContract.txt as its reference, it would review any diff
or new file placement and flag violations (e.g. Streaming code writing
to the authoritative Postgres store instead of Signal Engine).

Tradeoff:
  + Reusable across the whole project life, catches architecture drift
    automatically, cheap to invoke once written.
  - No value until there's actual code/diffs to review — building it
    now means writing it against a hypothetical, and you'd likely
    tune it once you see real diffs anyway.
  - Extra moving part to maintain if the domain contract changes.

Recommendation: defer until after first component is scaffolded, then
build it against real code.

4. HOOKS  (.claude/settings.json)
=====================================================================
What they are: deterministic shell commands the HARNESS runs automatically
on events (file edit, before/after tool use, session stop, etc.) — not
something I decide to do, something that always fires. This is the only
mechanism for "every time X happens, always do Y" — memory/CLAUDE.md
instructions are guidance I follow, hooks are enforced.

Relevant candidates given your locked Standards.txt tooling choices:
  - PostToolUse hook: auto-run `ruff check --fix` + `black` on any .py
    file after I edit it, so formatting/lint is never a manual step.
  - PreCommit-style hook (or a git pre-commit hook, separate from Claude
    hooks): block commits if `pytest -m unit` or lint fails.
  - Stop hook: notify you (desktop notification / sound) when I finish
    a long task.

Tradeoff:
  + Cheap to set up, deterministic — won't silently drift like a prompted
    convention might.
  + Can be set up now, ahead of code existing (the hook just won't fire
    until matching files exist).
  - Wrong/too-aggressive hooks (e.g. auto-formatting before you've
    reviewed a diff) can be annoying; needs a little tuning.
  - Requires the tools referenced (ruff/black) to actually be installed
    once components exist — currently they aren't (empty pyproject.toml
    files).

Recommendation: reasonable to set up now since the tool choices are
already locked in Standards.txt — low regret. The `update-config` skill
can do this for me when you're ready.
